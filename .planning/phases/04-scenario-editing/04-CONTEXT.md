# Phase 4: Scenario Editing - Context

**Gathered:** 2026-04-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Фаза добавляет сценарный пересчет поверх уже импортированных фактов из YouTrack и базового cost engine. На выходе менеджер должен иметь возможность добавить дополнительные часы прямо на карточках задач, сразу увидеть прогнозные затраты и прогнозную рентабельность рядом с текущими значениями, и при этом не смешивать эти ручные изменения с каноническим snapshot из YouTrack.

</domain>

<decisions>
## Implementation Decisions

### Scenario baseline
- **D-01:** Базой расчета остается исходный бюджет требования.
- **D-02:** Phase 4 не вводит произвольное редактирование бюджетов как отдельный постоянный сценарий; основная цель фазы — понять, сколько дополнительных часов и денег нужно согласовать с заказчиком.

### Additional hours workflow
- **D-03:** Дополнительные часы добавляются прямо на карточке конкретной задачи в дереве требования.
- **D-04:** Сценарные дополнительные часы должны учитываться только в прогнозной затратной части и не изменять фактические трудозатраты snapshot из YouTrack.
- **D-05:** Стоимость дополнительных часов считается по исполнителю, уже назначенному на задаче.

### Scenario output
- **D-06:** После добавления дополнительных часов экран должен одновременно показывать текущую рентабельность и прогнозную рентабельность.
- **D-07:** После добавления дополнительных часов экран должен одновременно показывать текущие затраты и прогнозные затраты.
- **D-08:** После добавления дополнительных часов система должна показывать сумму, которую нужно согласовать, чтобы выйти на целевые `20%`.

### Scenario lifecycle
- **D-09:** Сценарий живет только на текущем экране и не сохраняется после перезагрузки страницы.
- **D-10:** Если пользователь запрашивает новый refresh из YouTrack при наличии сценарных часов, система должна сначала спросить подтверждение перед их сбросом.

### Explainability
- **D-11:** Для контекста расчета достаточно показывать только `root issue`.
- **D-12:** Для контекста расчета достаточно показывать время последнего refresh из YouTrack.

### the agent's Discretion
- Конкретная форма ввода дополнительных часов на карточке задачи, если она остается быстрой и однозначной для PM.
- Визуальное расположение текущих и прогнозных метрик на экране, если они остаются видны одновременно и не смешивают факт со сценарием.
- Формулировка confirm-диалога перед refresh при наличии сценарных часов.

</decisions>

<specifics>
## Specific Ideas

- Пользователю нужен рабочий PM-flow, а не абстрактная форма по направлениям: дополнительные часы добавляются на уровне конкретной задачи.
- Сценарные часы нужны для быстрого ответа на вопрос, насколько просядет рентабельность и сколько денег надо дополнительно согласовать с заказчиком.
- История сценариев и долговременное хранение пока не нужны: v1 достаточно краткоживущего сценария в рамках текущего экрана.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `app/page.tsx` уже объединяет snapshot, budgets, cost summary и direction breakdown в одном workspace.
- `ScopeTree` уже рендерит карточки задач и предупреждения, поэтому сценарный ввод дополнительных часов логично встраивать туда же.
- `calculateRequirementCost` и `calculateProfitability` уже отделяют фактические деньги от UI-слоя и могут стать базой для прогнозных расчетов.

### Established Patterns
- Проект уже держит канонический snapshot YouTrack отдельно от пользовательского представления; Phase 4 должна сохранить это разделение и не мутировать импортированные факты.
- Все предыдущие фазы предпочитали явные blocked/confirm states вместо тихих неочевидных side effects.
- Текущий workspace построен вокруг одного `root issue` и одного ручного refresh, так что сценарный слой должен оставаться локальным для этого экрана.

### Integration Points
- Нужен локальный слой scenario state поверх результата `RootIssueForm`.
- Нужна связка scenario state с карточками задач в `ScopeTree`.
- Нужен прогнозный cost/profitability pass, который использует текущий snapshot, исходный бюджет и добавленные вручную часы.
- Нужен confirm gate перед повторным refresh, если в локальном scenario state уже есть изменения.

</code_context>
