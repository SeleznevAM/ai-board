# Phase 1 Research: YouTrack Data Contract

**Phase:** 1
**Name:** YouTrack Data Contract
**Date:** 2026-04-07
**Status:** Complete

## Objective

Понять, что нужно знать для качественного планирования Phase 1, где продукт впервые работает с `root issue` YouTrack и строит дерево scope для будущего расчета рентабельности.

## What This Phase Must Lock

Phase 1 не считает рентабельность и не собирает полные worklog-данные. Ее задача уже на старте зафиксировать, по каким правилам система:

1. принимает `root issue`;
2. определяет, что входит в иерархию требования;
3. строит дерево задач;
4. решает, можно ли доверять scope текущего пользователя;
5. выдает либо дерево, либо понятную ошибку.

Если на этом этапе контракт scope будет размытым, последующие фазы посчитают затраты по неверной границе и продукт станет недостоверным.

## Planner-Relevant Findings

### 1. Hierarchy semantics must stay narrower than "all linked issues"

Для этой фазы уже зафиксировано пользовательское решение: в v1 поддерживается только базовая иерархия `parent -> subtasks -> nested subtasks`. Это правильное ограничение для первой версии, потому что:

- YouTrack links могут быть направленными, настраиваемыми и использоваться для разных смыслов, не только для декомпозиции требования;
- если смешать subtasks и произвольные связи уже в Phase 1, план неизбежно раздуется до моделирования бизнес-семантики конкретной инсталляции YouTrack;
- следующая фаза сможет строить ingestion только на одном понятном контракте.

**Вывод для плана:** нужны отдельные задачи на формализацию поддерживаемой модели дерева и на явное закрепление того, что неиерархические связи в v1 не входят в scope.

### 2. Current-user visibility is part of the business contract, not just auth plumbing

Пользователь выбрал модель, где расчет идет в контексте прав текущего пользователя. Это значит:

- дерево scope зависит от видимости текущего пользователя;
- неполная видимость дерева не является "частичным успехом", а блокирует результат;
- продукт не имеет права достраивать скрытые ветки через сервисный доступ или приблизительные допущения.

**Вывод для плана:** нужно отдельно описать и протестировать visibility contract:
- доступная root issue;
- недоступная root issue;
- частично доступное дерево;
- полностью доступное дерево.

### 3. Phase 1 should treat partial scope as a hard failure

Это самое важное решение для доверия к продукту. Если хотя бы одна часть дерева недоступна, система не должна показывать scope как валидный для будущего расчета. Даже если визуально удается построить часть дерева, для продукта это блокирующее состояние.

**Вывод для плана:** должны появиться задачи на:
- определение критериев "дерево полное / дерево неполное";
- контракт ошибки для partial visibility;
- acceptance criteria, которые запрещают показывать "успешный" результат при неполной видимости.

### 4. Root issue handling should be separated into distinct failure modes

Для Phase 1 важно различать как минимум четыре сценария:

1. `root issue` существует и доступна;
2. `root issue` не существует;
3. `root issue` существует, но недоступна;
4. `root issue` существует и не имеет дочерних задач.

Последний случай не должен считаться ошибкой: дерево строится из одной корневой задачи.

**Вывод для плана:** это не одна "validation task", а отдельные acceptance branches. Их лучше закрепить в task-level acceptance criteria и в must_haves.

### 5. Tree presentation is minimal but still product-visible

Хотя фаза инфраструктурная, результат уже пользовательский: нужно показать дерево задач с вложенностью. При этом пользователь специально не хочет:

- показывать игнорируемые неиерархические связи;
- перегружать экран диагностикой "что не вошло из-за неподдерживаемых ссылок".

Следовательно, UI этой фазы должен быть минимальным и сфокусированным:

- вход по `root issue`;
- результат в виде дерева;
- явные ошибки для отсутствующей или недоступной root issue;
- блокировка результата при partial visibility.

**Вывод для плана:** задачи UI должны быть ровно настолько глубокими, чтобы отразить контракт данных, а не строить полноценный dashboard.

## YouTrack Concepts That Matter For Planning

Даже без точной привязки к будущему клиенту API planner должен учитывать следующие сущности:

- **Issue / root issue**: стартовая точка построения scope.
- **Subtask hierarchy**: единственный допустимый источник вложенности для v1.
- **Readable issue identifier vs internal id**: пользователь вводит человекочитаемый ключ, а система может работать с внутренним id после резолва.
- **Current-user visibility**: ответ API и доступность дочерних веток зависят от прав вызывающего пользователя.
- **Cycles / duplicate references defense**: даже при ожидании дерева код обхода должен защищаться от повторного посещения узлов.

**Вывод для плана:** нужен отдельный слой нормализации дерева scope, а не смешение UI, валидации ввода и обхода YouTrack в одном месте.

## Recommended Acceptance Boundaries For Phase 1

Phase 1 можно считать успешно спланированной и затем успешно реализованной только если после выполнения будет верно следующее:

1. Пользователь вводит `root issue` и система пытается построить scope только по subtask-иерархии.
2. Если root issue не существует, отображается отдельная ошибка "not found".
3. Если root issue недоступна текущему пользователю, отображается отдельная ошибка доступа.
4. Если root issue доступна и не имеет детей, показывается дерево из одного узла.
5. Если любая часть поддерживаемой иерархии недоступна, успешный результат не показывается.
6. Неиерархические связи не участвуют в scope и не появляются в UI.
7. Успешный результат Phase 1 визуализируется как дерево задач с вложенностью.

## Explicit Non-Goals For Phase 1

Чтобы planner не раздувал объем работ, в Phase 1 не нужно включать:

- расчет фактических трудозатрат;
- сбор или агрегацию worklog-данных;
- распределение по ролям и направлениям;
- расчет бюджета, себестоимости и рентабельности;
- поддержку неиерархических связей;
- продвинутую explainability по исключенным связям;
- сервисный технический аккаунт с расширенным доступом.

## Risks That Should Become Plan Tasks

### Risk 1: Hidden ambiguity between "no children" and "children not visible"

Если модель данных не различает эти состояния, продукт может ошибочно считать неполное дерево валидным листовым узлом.

**Plan implication:** нужна отдельная задача на контракт полноты дерева и семантику partial visibility.

### Risk 2: Traversal logic grows into ingestion logic too early

Если в Plan 1 сразу тащить сетевой слой, обработку worklogs и доменную нормализацию будущих фаз, фаза потеряет фокус.

**Plan implication:** ограничить Phase 1 определением и демонстрацией scope contract. Полный ingestion оставить на Phase 2.

### Risk 3: UI starts exposing unsupported semantics

Если дерево начнет отображать произвольные связи или "почти вошедшие" задачи, пользователь получит неверное представление о том, что реально считается частью требования.

**Plan implication:** UI этой фазы должен быть жестко подчинен контракту `subtasks only`.

### Risk 4: No protection from duplicates or cycles

Даже если ожидается дерево, реальная интеграция должна защищаться от повторного добавления узлов, чтобы будущий scope не дублировался.

**Plan implication:** в плане должна быть отдельная задача или acceptance criterion на defensive traversal semantics.

## Suggested Plan Shape

Для этой фазы логично ожидать 2-3 плана:

1. **Contract and domain plan** — формализовать правила scope, ошибки и критерии полноты.
2. **Traversal and scope resolution plan** — определить и реализовать технический путь построения дерева по subtask-иерархии.
3. **Minimal presentation plan** — показать результат пользователю как дерево и корректно отразить ошибки/блокировку.

Если planner сможет объединить первые два пункта без потери конкретики, фаза может уложиться в 2 плана.
